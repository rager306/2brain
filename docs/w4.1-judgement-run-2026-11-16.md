# Judgement run: subq-snap-1.2 over a labelled sample (W4.1 phase 2)

Status: measured 2026-11-16. Cost of the whole experiment: **$0.0019 per pass**, four passes run while
fixing the harness. The key lives in `<repo>/.env` (gitignored, mode 600) and the harness reads it from
there; nothing in this document or in the repository contains it.

## What was run

50 notes from `/root/vault`, stratified by type and seeded with hubs and with descriptions a screen
flagged as possibly stale (`tools/judgement/labelled.json`, hand-labelled). Three questions per note —
`noul` stale-or-not, `choice` over the nine types, `noul` duplicate-of-a-named-candidate — for 150
questions, 188 831 characters ≈ 47 208 tokens per pass. Model `subq-snap-1.2`, `POST /v1/systemone`,
one request per note, four in flight, ~0.6 s per request.

| question | decided | accuracy | yes precision | yes recall | uncertain |
|---|---:|---:|---:|---:|---:|
| `description_matches_body` (label: stale) | 43 | 0.884 | 0.667 | **0.333** | 7 |
| `type` (choice, nine) | 48 | 0.729 | — | — | — |
| `duplicate` | 50 | 0.980 | **1.000** | 0.889 | 0 |

Base rates, which is why accuracy is the wrong single number: 10 of 50 notes are stale and 9 are
duplicates, so answering "no" every time scores 0.80 and 0.82 respectively.

## Two bugs in the harness, found by running it

1. **The request shape was wrong and every request failed.** The harness sent `questions` as a *list*
   of `{id, type, instructions, true, false}`. The vendor takes an *object* keyed by id with the
   type-specific parts under `criteria`: `{true, false}` for `noul`, `{option: description|null}` for
   `choice`, an ordered list of level descriptions for `score`. First run: 50 of 50 failed. Measured,
   fixed, and the shape is now in the code with the date.
2. **The polarity was inverted in scoring.** The model answers "does the description still describe the
   body?" (yes = accurate); the hand label is `stale_description` (yes = stale). Comparing them
   directly scored a calibrated judge at **0.116** — the number the first working run printed. Inverted,
   the same answers score 0.884. The model was never the problem; our comparison was.

## What the numbers say

- **Duplicates: adopt.** Precision 1.000, recall 0.889 at threshold 0.7, and stable up to 0.99. This is
  the question the backlog wanted answered before creating a note that already exists.
- **Stale descriptions: not yet.** Recall 0.333 — it finds one stale note in three, with two false
  positives and seven answers in the "uncertain" band. As a *detector* it is not usable; as a *triage
  filter that only confirms* it could be, if the workflow is "ask about the notes a cheaper screen
  flagged", which is exactly how the sample was built.
- **Type: adjacent-class confusion, not noise.** 35 of 48 correct, and every off-diagonal is a
  neighbour: `insight → extract` (3), `error → insight` (2), `decision → pattern/insight`,
  `extract → pattern/insight`, `moc → claim`. That is a taxonomy problem as much as a judge problem —
  `extract` (what a source says) versus `insight` (what we concluded) differs by provenance, which
  the excerpt alone may not show.

## What the experiment cost and proved

- The wire is ours: the vendor speaks the same `systemone` shape as our local `jev`, so a local judge
  can be compared on the same labelled file without rewriting the harness (`--endpoint`).
- Cost and latency are small enough for a batch pass (2 cents, ~30 s for 50 notes), and far too large
  for the serving path (0.6 s per request against a 15 ms read budget).
- The egress is real: 188 k characters of note text per pass left the host. That is the policy
  decision the assessment flagged, and it was taken explicitly by supplying a key; the default
  remains local-first.

## Next experiment, not run

Change the staleness question from a yes/no to "name the claim in the description that the body does
not support, or say none" (a `choice` over the candidate claims, or `score` over support), because a
yes/no gives the model no way to express "the description is vague" — which is most of what the hand
labels called stale. Then re-measure recall on the same 50 notes before spending another cent.

## Second experiment: the shape of the staleness question

Same 50 notes, same model, one request each, ~$0.002. Instead of "does the description still
describe the body?" (`noul`) the note was asked a five-way `choice`: `supported` | `vague` |
`missing` | `contradicted` | `another_subject`. Binary detection = anything but `supported`.
Reproduce with `python3 tools/judgement/stale_choice_probe.py`.

| rule | tp | fp | fn | precision | recall |
|---|---:|---:|---:|---:|---:|
| `noul`, p ≤ 0.3 | 2 | 1 | 8 | 0.667 | 0.200 |
| `noul` at its best threshold (0.7) | 2 | 1 | 8 | 0.667 | 0.200–0.333 |
| `choice`, confidence ≥ 0.5 | 5 | 13 | 5 | 0.278 | 0.500 |
| `choice`, confidence ≥ 0.8 | 5 | 9 | 5 | 0.357 | 0.500 |
| union of the two | 5 | 13 | 5 | 0.278 | 0.500 |
| intersection of the two | 2 | 1 | 8 | 0.667 | 0.200 |

The sample holds 10 stale notes; the choice run left 8 of them decided and 2 uncertain.

What this says:

- **The shape moves the trade-off, not the frontier.** The yes/no variant is precise and shy
  (0.67 / 0.33); the five-way variant is sensitive and noisy (0.36 / 0.50). Combining them does not
  beat either corner — the union just adds false positives, the intersection collapses to the
  yes/no answer.
- **Four of the five options went unused.** Every failure it reported came back as `missing`; it
  never chose `vague`, `contradicted` or `another_subject`. That is the interesting result: given a
  holistic judgement over a whole body excerpt, the judge's only move is "I cannot find this claim",
  which is also the move a false positive makes.
- **Therefore the next design is per-claim, not per-note.** Extract the description's claims (a
  generation task, outside this API), then ask a `noul` per claim against the body, then a note is
  stale when one claim fails with confidence above a bar. That is three cheap calls per note instead
  of one, and it is testable on the same 50 labels — but it needs a claim extractor, which is the
  first thing in this line that would need a generative model rather than a judge.

**Decision for the backlog:** P0-3 (stale-description detector) is **not solved** by the judgement
layer as it stands. The honest product answer is a *triage* pass: the choice variant at
confidence ≥ 0.5 flags 18 of 50 notes and catches half the stale ones, which is a review set a human
can clear in minutes — cheaper than reading all 50, but not an automation.
